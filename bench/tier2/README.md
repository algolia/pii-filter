# Tier-2 PII NER receipts (latency + French mini-eval)

The two measurements the research report (`docs/research-sota-2026-07.md`) flagged as
missing everywhere: **CPU latency/memory per ~KB** and a **French/e-commerce accuracy
eval with bootstrap CIs**, for the two Tier-2 candidates. These are first real numbers on
a proxy machine, not final production figures.

## Layout

| File | What |
|---|---|
| `generate_dataset.py` | Deterministic (seed 42) generator: French PERSON + ADDRESS samples with exact char-span labels, search-query and support-message shapes, ~25% negatives. |
| `dataset.json` | The generated n=200 set (committed; re-runnable, raw data is not). |
| `models.py` | Candidate wrappers normalised to PERSON / ADDRESS spans; taxonomy mapping documented inline. |
| `bench_latency.py` | CPU latency + peak RSS bench; warmup + timed iters; cold start separate; JSONL append per measurement. |
| `eval.py` | Span-level P/R/F1 per entity, exact + partial-overlap, 95% bootstrap CIs (10k). |
| `results_latency.jsonl`, `results_eval.json` | Recorded outputs. |
| `requirements.txt` | Bench-only deps (NOT toolkit deps). CPU torch. |

## Candidates

- **GLiNER2-PII** — `fastino/gliner2-privacy-filter-PII-multi` (0.3B, mdeberta-v3-base
  encoder), via `gliner2[local]`. Accuracy-lean pick. Fully functional.
- **gliner-pii-edge** — `knowledgator/gliner-pii-edge-v1.0`, UINT8 ONNX (`model_quint8.onnx`,
  ~46 MB), via `gliner` + onnxruntime. Footprint-lean pick. **Detections non-functional**
  in `gliner==0.2.27`: the vendor's own model-card example returns zero entities at
  threshold 0.3 across PyTorch and ONNX (quint8/fp32) paths; fp16 ONNX fails to load
  (onnxruntime fp16 type error). Its encoder is a very new `jhu-clsp/ettin-encoder-32m`
  (ModernBERT) that the current `gliner` release does not run correctly. Only its
  forward-pass **latency/footprint** is reported; accuracy is unmeasurable here.

## Taxonomy mapping (documented — mismatch deflates scores if left implicit)

Both models emit a fine PII taxonomy; the toolkit gold is coarse PERSON / ADDRESS.

```
GLiNER2-PII: person, full_name              -> PERSON
             address, street_address, city, postal_code -> ADDRESS
edge:        person, full name              -> PERSON
             address, street address, city, postal code -> ADDRESS
```

Overlapping/adjacent same-type predicted spans are merged into their union before scoring.

## Reproduce

```bash
python -m venv venv && . venv/bin/activate
pip install torch --index-url https://download.pytorch.org/whl/cpu
pip install -r requirements.txt

# 1. regenerate the labeled set (downloads the INSEE prenoms into data/ on first run)
python generate_dataset.py --out dataset.json --n 200 --seed 42

# 2. accuracy (bootstrap CIs). --edge-dir optional; edge accuracy is non-functional.
python eval.py --dataset dataset.json --out results_eval.json

# 3. latency (run 1-thread as a separate pinned process)
python bench_latency.py --model gliner2 --threads default --out results_latency.jsonl
OMP_NUM_THREADS=1 taskset -c 0 python bench_latency.py --model gliner2 --threads 1thread \
    --out results_latency.jsonl

# 4. charts
python ../../docs/assets/render_tier2_f1.py
python ../../docs/assets/render_tier2_latency.py
```

## Data sources

Every sample is synthetic: no address is a real place and no name pair describes a real
person.

- ADDRESS — generated by `synth_addresses` in the generator: invented commune names (none
  is in the official commune list, checked against geo.api.gouv.fr on 2026-11-16), generic
  street names and a Lozère-style `48xxx` postal code.
- PERSON first names — aggregate counts from INSEE *fichier des prénoms depuis 1900*, national parquet mirror.
- PERSON surnames — INSEE most-common family-name ranking, baked as a documented list in
  the generator (INSEE patronyme micro-files are not a single stable download).

Raw data files are downloaded on demand into `data/` and are **not committed** (dumps);
only `dataset.json` is.
